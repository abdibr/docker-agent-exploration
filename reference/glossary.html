Glossary — Docker Agent workspace

Every term below is grounded in this repo's seven verified examples and the official Docker Agent docs — one line each, with the example that proves it. Companion page: the example map.

Core concepts

Docker Agent ex01
Docker's open-source AI agent builder & runtime. You author a declarative YAML config; the docker agent CLI (a Docker Desktop 4.63+ plugin) runs it. No wrapper code, SDK, or client needed.
cagent
The same tool's old name (Docker Desktop 4.49–4.62). Why older tutorials and search hits say “cagent”.
Agent config (agent.yaml) ex01
The whole program: model entries, agent definitions (role, instruction, tools), and connections. Key names are pinned by the official agent-schema.json; validate with YAML language-server or --dry-run.
Transcript ex01–03
The printed record of a run: every tool call, its args/result, then the final answer. --exec prints it to stdout. This — never the exit code — is what you judge.
Exit-0 discipline ex01–03
Failures (denied calls, missing toolsets, degenerate loops) still exit 0. Machine assertions must check the transcript or the protocol surface, not return codes.
Verification seam every ex
The repo's testing pattern: exactly one headless command per example, asserted on external behavior only. Phased: config sanity → spend-y verify.
Model swap ex01
Changing the model = editing one model: value in the named entry (gemma4:latest ↔ glm-5.3-flash:cloud). Cloud use in this workspace only in pre-approved smoke tests.

Config keys (agent.yaml vocabulary)

models: + named entry ex01
A friendly name (e.g. gemma4_local) wrapping provider:, model:, and a description:. Agents reference it by name, so models are swappable in one line.
provider: ex01
Which backend serves the model. This workspace pins the built-in ollama provider → the local Ollama daemon at localhost:11434. Daemon must be running.
agents: / root ex01
The agent you actually talk to (name is convention here: root). Extra named agents appear in Ex04 as roles, in Ex05/06 as served metadata, in Ex07 as ACP sessions.
description: ex03·05·06
Not just docs: it surfaces as the MCP tool description (Ex05) and feeds the A2A agent card (Ex06).
instruction: ex01
The agent's prompt — role and behavioral rules, seen by the model every turn. Good rules make verification deterministic (ex01: “read the file first; quote exact values”).
max_iterations: ex01·04
Turn budget, a runaway-loop fuse. ex01 uses 20; ex04's lead needs 12 because delegation costs turns.
toolsets: ex01·03
Declarative capabilities. Built-ins in this repo: filesystem, shell, think. Wrong/missing toolsets are a classic silent failure — see debug toolsets.
allow_list: ex01
Restricts a toolset (filesystem sandboxed to ["."] — its working directory). Restrictive only; the default without it is unrestricted.
sub_agents: ex04
In-process role delegation inside one config — lead + specialists, zero protocol machinery. Context boundary is the handoff: sub-agents see only what the lead forwards. Try this flavor first. MCP refs are root-only (a sub-agent cannot carry MCP tool refs).

Running (run surfaces)

docker agent run agent.yaml ex01+
Interactive TUI — terminal chat with your agent. For demos and exploration.
--exec "task" ex01+
Headless: runs one task non-interactively, prints the full transcript to stdout, exits when done. The verification verb.
--json ex01+
NDJSON event stream instead of prose — one JSON object per line (~150 events for a trivial prompt). For machine-readable evidence.
stdin pipe ex01+
echo "task" | docker agent run cfg.yaml - --exec — task via stdin instead of an argument. This workspace's escape hatch for Windows PowerShell 5.1 quote-mangling.
--dry-run ex02+
Validates the config without touching a model — the free pre-flight gate before any spend.
debug config / debug toolsets ex03
Print the canonical effective config / the concrete tool list (this one starts toolsets and images). The Ex03 lessons: a missing tool image only shows here and in errors.
serve mcp|a2a|api|chat|acp
Expose the agent as a service — see example map and the five surfaces table below.

Safety modes

Safety ladder
default | strict | balanced | restricted | autonomous — session tool-call policy. Serving surfaces announce their policy in a startup banner and default to restricted.
--safety restricted ex01+
Fail-closed unattended profile: obviously-safe calls auto-approve; the rest are silently denied — the denial appears only as a transcript line, never a prompt. The repo's verification default.
--yolo / autonomous ex02·03
Auto-approve everything, one deliberate command at a time. The MCP examples verify this way because restricted denies MCP calls.
ACP session modes ex07
In an ACP session the editor negotiates and switches mode (and model) from its UI per session.

Protocols & serving

MCP ex02·03·05
Model Context Protocol: standard JSON-RPC tool interface. The agent is the client in ex02/ex03 (it calls tools); the server in ex05 (an MCP client consumes the agent as one tool). Moves synchronous tool calls — not task handoff.
MCP catalog ref ex02
ref: docker:duckduckgo — a proven Docker-hardened tool from the public Agent Catalog, run per-call in a digest-pinned, egress-restricted container. Zero code, strongest isolation.
MCP custom server ex03
Your own ~100-line MCP server, no SDK, containerized and tagged; started by Docker Agent per session (--rm teardown). Use the tools: allow flag to pre-approve its calls.
A2A ex06
Agent-to-Agent protocol: agents discover each other via an agent card and exchange tasks (state machine + artifacts) over HTTP JSON-RPC on 127.0.0.1:8082. 331–496 ms overhead beyond the model; task state lives server-side (context/task IDs).
Agent card ex06
A2A's discovery document (name, description from the config, skills, URLs). The description: you wrote in the config ends up here.
ACP ex07
Agent Client Protocol: the editor (Zed) spawns the agent as a subprocess speaking stdio JSON-RPC — sessions, streaming, permission prompts in the editor. Zero serve flags; mode/model negotiated from the editor.
Documented but never probed in this workspace: serve api (REST/sessions + bearer auth, 127.0.0.1:8080) and serve chat (OpenAI-compatible completions, 127.0.0.1:8083). Excluded from every decision rule — don't teach them as verified.
