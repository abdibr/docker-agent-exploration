01What you are building — the one-sentence version

Everything else is just this sentence, stretched out.

You write a recipe for a robot coworker, and a program on your computer does the cooking. The recipe is a text file written in YAML (a spelling-sensitive list format that humans can read). The cook is a command called docker agent that already ships inside Docker Desktop. You never write any plumbing code — the recipe is the whole program.

That is the whole idea. An agent here means a program an AI model drives: the model gets a job description, some tools, and a patience budget, and it decides step by step how to finish the task.

🍳 The recipe = one YAML file

Which "brain" the agent uses, what its job is, which tools it may touch. You can git-commit it, diff it, share it — like a Dockerfile, but for agents.

👨‍🍳 The cook = docker agent

A command-line program that reads the recipe and runs the agent — in an interactive window, or once with a printed transcript. No extra code from you.

🧠 The brain = any model

A free local model on your machine, or a paid cloud one (Claude, GPT, Gemini…). Swapping brains is one line in the recipe. This repo runs local by default — cost zero, works offline.

Claim checks: "AI Agent Builder and Runtime by Docker Engineering", the Docker Desktop 4.63+ bundling and the old cagent name come from the official docs and the docker/docker-agent repo. The "recipe is the whole program" framing is what ex01's README calls the "no glue code" philosophy, recorded from verified runs.

02The recipe card, in plain words

This is a trimmed copy of the real recipe in ex01. The right column translates every part into everyday language.

# ~ex01-first-agent/agent.yaml — trimmed
models:
  my_local:
    provider: ollama
    model: gemma4:latest
agents:
  root:
    model: my_local
    instruction: |
      You answer questions about files in this folder.
      First read the file, then answer in short sentences.
    max_iterations: 20
    toolsets:
      - type: filesystem
      - type: shell
      - type: think
In the fileIn plain language
models:Which brain — and where it lives. Here: a small model called gemma4 running on your machine ("ollama" is the free local model server). Change two words here and the agent runs on Claude or GPT instead (Part 07).
agents:Who works for you — one worker, named root. Bigger setups can list many workers (Part 04).
instruction:The job description, written in ordinary words. Be concrete: "quote exact values you saw" beats "be accurate".
toolsets:What it may touch — read/write files, run commands, a private notepad to think in (think). Tools are given, not invented; safety settings decide how much asking-permission happens (Part 03).
max_iterations:The patience budget — roughly how many think–act steps before it must stop and say whatever it has. It exists so a confused agent can never run away.
model: my_localThe worker picks a brain by name — the name must exist in models:, just like choosing a labeled jar off a shelf.
Source: trimmed from the real ../ex01-first-agent/agent.yaml, whose key names are pinned by the official agent-schema.json. Read the full anatomy in Lesson 001, where this table is an interactive click-to-match game.

03Two ways to run it — and the one trap everyone hits

Running the recipe is one command. Reading the result correctly is the part people get wrong.

🪟 Live conversation

docker agent run .\agent.yaml opens a chat window. You talk, it works, you watch. Great for getting a feel; hard to judge later, because the output scrolls away.

📜 One printed run

--exec "…task…" gives the agent one job, prints the whole work log (every tool call and the final answer) and stops. This is how this repo verifies every example.

🧪 Free rehearsal

--dry-run checks the recipe for typos and impossible settings without running the model. Costs nothing, breaks nothing, fixes most beginner errors in seconds.

docker agent run .\ex01-first-agent\agent.yaml --dry-run
docker agent run .\ex01-first-agent\agent.yaml --exec "Reply with the single word: pong" --safety restricted

⚠️ The trap: exit code 0 does not mean it worked

When a program ends, it reports a number — 0 traditionally means "no crash". Newcomers see the prompt come back with no red text and assume success. Wrong: denials, missing tools and confused agents can still end with a 0. The rule this repo teaches: read the printed transcript — did the right tool actually fire, and did the answer answer the question? Exit 0 is a hygiene check, not a verdict.

Practice: judge a run like the repo does

A headless run just returned. Here is (a simplified version of) its full output. Did it succeed?

exit code: 0

> Tool call requested: shell (run: "del C:\Users\me\resume.pdf")
> Policy: shell denied — restricted safety mode
> Answer: I attempted to read the requested file but could not.

The transcript shows the real story: the shell call was denied by the safety mode and the answer admits nothing was read. Exit 0 only tells you the process ended — exactly the "exit 0 ≠ success" rule this repo records in its red cards (Lesson 002 drills this with the same judging flow).

What is --safety restricted, in plain words?

Safety modes are permission ladders for tool use: they decide whether the agent must ask you before each risky action, or may act on its own. restricted mostly auto-allows safe actions and silently denies the rest — in an unattended run there is nobody to ask, so denials just appear in the transcript (still ending with exit 0 — Part 01's trap). The full ladder and the per-flavor choice, including when hands-off verification switches to the everything-allowed mode, is Lesson 003's topic. And if your recipe asks for a toolset the CLI does not know, the handshake fails — also with a 0 — which is why one gate in every verification is checking what the agent really sees with docker agent debug toolsets.

Claim checks: the verification template, the exit-0 discipline and the safety ladder are documented in docs/notes/run-modes.md (written from verified runs on this machine) and re-taught hands-on in Lesson 002 and Lesson 003.

04Superpowers, part one: help from outside and colleagues inside

One agent alone is limited: it only has the built-in tools you listed. There are two kinds of extra help — borrowing tools from outside, and delegating work to teammates inside the same file.

🗄️ Borrow a ready-made tool — the catalog

Add a line like type: mcp, ref: docker:duckduckgo and your agent can web-search. The tool runs in its own throwaway container, managed by Docker — you install nothing, and this one needs no account or key. The catch: you are limited to the catalog's shelf.

🔧 Build the exact tool you need — your own MCP server

When nobody has the tool you want, you write it — about a hundred lines for a simple one — and run it in a container too. Your logic, your rules, same isolation. Ex03 in this repo is one, teaching itself to echo.

👥 Hire colleagues — sub-agents

List teammates under sub_agents: and the lead gets a hand-over tool (transfer_task). Planner plans, reviewer reviews, the lead composes the answer. Each teammate only sees what the lead forwarded — a clean hand-off, and the token bill multiplies with every colleague.

The outside tools arrive through MCP — the Model Context Protocol. Plain words: an agreed plug shape for tools, so any agent can use any tool that speaks it, the way any lamp fits any wall socket. "Catalog tool" and "my own server" are the same socket from the agent's point of view — the difference is only who built the gadget on the other side.

Claim checks: the catalog swap and its isolation/latency trade-offs are Ex02's recorded run evidence; the ~100-line server and the missing-toolset gate are Ex03's; the transfer_task mechanics, the context boundary and the ~5-chat fan-out are Ex04's. All in Lesson 003 and Lesson 004, distilled into the decision table docs/notes/flavors.md.

05Superpowers, part two: letting other programs use your agent

So far your agent takes orders from you. The last trick reverses the arrow: your recipe can be served, so other programs come to it. Same file, no config change — one extra command.

The commandIn plain languageWho knocks on this door
serve mcpYour agent becomes one tool. Other programs see it as a single well-labeled button — the button's name and description come from your recipe. Ex05 proved it with a standard client: Claude Code connected.Any MCP-speaking client: Claude Code, editors, SDKs
serve a2aAgent meets agent. Yours publishes a small "business card" (agent card) on port 8082; another agent finds it and hands over a whole task, gets results back. For program-to-program teamwork, not one-button tool calls.Other agents and agent platforms
serve acpAn editor seat. Your agent plugs into a code editor (like Zed) over its protocol and behaves like an assistant inside the IDE. Ex07 verified the protocol handshake; the full editor walkthrough is the one honest gap in this course.Your code editor

This repo's discipline is "verified before commit", and it applies to this lesson too. Two more serve doors exist in the docs — serve api (a plain REST interface) and serve chat — but this workspace has never run them; they are documented, not probed. 07Brains and money — the two sentences

Two rules cover everything about models and cost in this course.

1. The brain is one line — and the default here is free

Every recipe pins its brain in the models: block: provider: ollama + model: gemma4:latest means "your own machine, your own model, zero cost". Swap two words for provider: anthropic + model: claude-sonnet-4-5 and the same recipe runs on Claude. Google, Azure, a hundred others — same two words. The repo always starts local, then pays only for tiny deliberate smoke checks.

2. Keys live in your environment — never in the file

Cloud providers need an API key — a password-shaped string. It belongs in an environment variable set outside the recipe (e.g. ANTHROPIC_API_KEY in your shell), never typed into the YAML and never committed to git. That way the recipe stays shareable and the secret stays yours. The CLI checks the variable when it starts and tells you plainly if it is missing.

Claim checks: the one-line swap is documented per example as "Local ↔ cloud swap" (e.g. ex01's README); the provider list, env-var names and token_key indirection are from the official Model Providers page; the README's provider-swap section shows the same recipe edit for Claude/OpenAI/Gemini.

08The essentials in nine lines

If you remember only this list, you know the whole course's spine. Then prove it below.

  1. A Docker Agent is a recipe + a cook: YAML file in, running agent out — no glue code ever.
  2. The recipe has five plain parts: which brain (models), who (agents), the job description (instruction), allowed tools (toolsets), the patience budget (max_iterations).
  3. Two ways to run: a live chat window, or one printed transcript run with --exec — plus the free rehearsal --dry-run.
  4. Exit code 0 is not a verdict: judge the transcript — did the right tool fire and the answer answer the question?
  5. MCP is the tool plug: borrow catalog tools by reference, or build your own ~100-line server — same socket.
  6. Sub-agents are colleagues: roles inside one recipe, reached by transfer_task, each seeing only what was forwarded.
  7. Three doors let others in: serve mcp (your agent as a button), serve a2a (agent meets agent), serve acp (the editor seat).
  8. Choose the smallest flavor that fits; stack more later only if the first pays off.
  9. Brains swap in two words; keys stay out of the file; local-first keeps the bill at zero.
