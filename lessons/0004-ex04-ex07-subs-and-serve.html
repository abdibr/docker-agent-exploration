Lesson 004 · Sub-agents & the serve family — delegation, MCP/A2A/ACP seats

One flavor needs no wire at all: ex04's sub_agents: delegation lives inside one YAML file. Then the direction flips — serve mcp (ex05), serve a2a (ex06), serve acp (ex07) put the same declarative config on a protocol seat. Learn the roles, the ports, and how to judge each wire.

ex04 sub_agents ex05 serve mcp ex06 serve a2a ex07 serve acp verified on v1.153.0 · 2026-11-13 Windows 11 · PowerShell 5.1

01One config, three agents — delegation without protocols

One YAML file builds a three-agent team: a lead plus a planner and a reviewer, wired with Docker Agent's built-in sub_agents: mechanism — still no server code, no protocols, no glue; the config is the whole program (ex04 README). Declaring sub-agents changes exactly one thing: the lead gets a dedicated transfer_task tool, and nothing else changes.

What one list buys

sub_agents: is an array of names of sibling agents: entries (it also accepts OCI refs). Listing them is what hands the lead its delegation tool.

Lead-only, by the toolsets. The planner and reviewer get think only — the proof is below. A sub-agent would need its own sub_agents: entry to delegate further (nested hierarchies).

Required arguments. The tool signature is exactly {agent, task, expected_output} — the tool description the model sees demands task and expected_output. Weak prompts may show the model inventing an expected_output; harmless, but worth reading in the transcript.

Not a conversation handoff. The sub-agent's answer arrives back as tool-result data; the lead stays in control and composes the final answer.

The real ex04 team — verbatim from ex04-sub-agents/agent.yaml (the models: entry kept above as a comment; lead 12, subs 6 iterations)

# models:
#   cloud_agentic:
#     provider: ollama
#     model: glm-5.3-flash:cloud     # ← swap to: gemma4:latest (same daemon, app sign-in not needed)

agents:
  lead:
    model: cloud_agentic
    description: Ex04 lead coordinator - delegates planning and review to its sub-agents
    instruction: |
      You are Ex04, the lead coordinator in the docker_agents exploration repo. Your
      team solves every task by delegation, not by you:

      - transfer_task once to the planner: give the planner the planning part of the
        task, phrased as one clear goal.
      - transfer_task once to the reviewer: hand over the exact plan text you received
        from the planner and ask the reviewer for a verdict on it.
      - Combine the two outputs in your final answer: first the plan you received from
        the planner, then the verdict you received from the reviewer.
      - Never write plan steps or the verdict yourself; if a sub-agent returns nothing
        usable, say so plainly instead of inventing content.
    max_iterations: 12
    toolsets:
      - type: think
    sub_agents:
      - planner
      - reviewer
  planner:
    model: cloud_agentic
    description: Planning specialist - turns a goal into a short numbered plan
    instruction: |
      You are the planner. Return exactly the plan requested: numbered steps, one line
      each, no preamble, no commentary, no alternatives.
    max_iterations: 6
    toolsets:
      - type: think
  reviewer:
    model: cloud_agentic
    description: Review specialist - checks a plan and returns a two-line verdict
    instruction: |
      You are the reviewer. You receive a plan text. Judge it and return a verdict of
      exactly two lines: line 1 the word Approved or the word Revise, line 2 the single
      reason. No preamble.
    max_iterations: 6
    toolsets:
      - type: think

The context boundary — why the reviewer is trustworthy

Each sub-agent gets its own chat, its own instruction, its own tool surface — and, crucially for the reviewer, a fresh view that contains only what the lead forwarded (here: the plan text, not the lead's framing of the task). That context isolation, tailored instructions per role, and a transcript that shows exactly who produced what is what plain tools cannot give you.

The model-free gate — prove the split before any token is spent

docker agent debug toolsets .\agent.yaml

Expected: lead → think, transfer_task · planner → think · reviewer → think — the same introspection gate Ex02/Ex03 added to the verification template; it catches a mis-wired team before any model spend.

The verification template (headless, from ex04-sub-agents/ — task text carries no quotes or apostrophes, so the same string works from PowerShell 5.1 and cmd.exe)

docker agent run .\agent.yaml --exec 'Delegate immediately. First use transfer_task once to send the planner sub-agent this task: produce a numbered three-step plan for safely renaming the git branch main to trunk in a git repository. Then use transfer_task once to send the reviewer sub-agent the plan you received and ask it to approve the plan or flag a missing step. Then answer with exactly two labeled parts. Part 1: the numbered plan you received from the planner. Part 2: the reviewer verdict you received.' --safety restricted

The observed transcript, in order (2026-11-13, docker agent v1.153.0 — exit 0, about a minute)

# 1 — the lead delegates to the planner:
Calling transfer_task( agent: "planner", expected_output: "A numbered list of exactly three steps…",
  task: "Produce a numbered three-step plan for safely renaming the git branch main to trunk in a git repository." )
# 2 — the planner's full nested chat returns as the tool result (it even used its own think tool):
transfer_task response → "1. Confirm the working tree is clean and no work is lost (`git status`)…"
# 3 — the lead forwards the exact plan text to the reviewer:
Calling transfer_task( agent: "reviewer", task: the planner's plan verbatim )
# 4 — the verdict comes back as tool-result data:
transfer_task response → "Revise" + the reason: the plan omits updating references to `main` …
# 5 — the lead composes: Part 1 = planner's three steps verbatim; Part 2 = reviewer's Revise verdict verbatim
# exit code: 0

Both transfer_task blocks and both response lines are the machine-checkable evidence — exit 0 alone proves nothing (Ex01's rule).

Cost fan-out: one task ≈ 5 model chats

A one-user-task run fans out into ~5 model chats — one lead turn set plus a full nested chat per sub-agent — so token spend multiplies; each agent is bounded by its own max_iterations: (lead 12, subs 6 here). That fan-out is why ex04 defaults to glm-5.3-flash:cloud: delegation choreography (plan → forward → review → compose) is multi-hop reasoning. The README's recorded billing: ~$0.15 per 1M input / $0.50 per 1M output tokens — a fraction of a cent per five-chat run.

The committed config stays on the cloud model by default; the local swap is a one-line edit for cheap iteration on the team shape: model: gemma4:latest (no app sign-in needed). The README's record: the same verification task did complete on local gemma4 in a rehearsal run here — correctly, if verbosely, several minutes versus about a minute on cloud; a small model can fumble the choreography (dropping a delegation, inventing the plan or verdict, looping). The cloud_agentic key is cosmetic after a swap.

Delegation is classified safe — the opposite of arbitrary MCP calls

Under --safety restricted — the fail-closed unattended profile — every transfer_task call was auto-approved on the verified run (checked empirically with a free local-gemma4 rehearsal before the cloud run; zero denials in the transcript). Contrast Ex02: the catalog MCP search call was denied under the same mode. Delegating to a declared sub-agent is classified safe; an arbitrary containerized MCP tool is not — so ex04's one verification command keeps the strict profile. Hold that thought — Part 02 shows what the serve family does with the same restricted default.

Naming trap

Do not name a sub-agent like a built-in tool (think, …) and do not duplicate an agent name — agent names feed the tool surface when the config is served. And remember that sub-agent chats run with the sub-agent's own toolsets: both subs used their think tool inside their nested chats. A sub-agent with write tools is a sub-agent that will use them — keep toolsets minimal per role.

Provenance: ex04-sub-agents README + agent.yaml, verified 2026-11-13 on docker agent v1.153.0 (exit 0, about a minute). Default-path prerequisite: Ollama daemon running and the Ollama app signed in — ollama list must show glm-5.3-flash:cloud. A future plugin version could change what restricted approves — cross-check the classification finding above if the CLI updates.

02The serve family — five seats for the same YAML (ex05–ex07)

Ex04 kept everything in one process. The serve family flips the agent's side with a single verb — the config stays declarative throughout, and ex05/ex06/ex07 add no toolsets on purpose (run-modes.md §15; phase-notes.md §6).

The whole family, verbatim from run-modes.md §19 quick reference

serve mcp — your agent is one tool in someone else's toolbox (ex05)

One tool per agent, named after the agent. tools/list returns exactly one tool for a single-agent config: name: root; a multi-agent config like ex04's team would surface every agent as its own tool, and omitting --agent exposes every agent. --tool-name overrides, only when exposing a single agent. Input schema: a required {message}; output schema promises {response}. The tool's description is the agent's description: field — the calling model reads it to decide when to invoke your agent, so write it like a tool description.

Annotations are generic, not semantic. The observed tool carries readOnlyHint: true even though a call runs a full LLM chat — do not read "no side effects" into them.

The answer travels twice. Text content came back as the JSON string of the answer while structuredContent.response was the typed value — prefer the typed field when your client supports structured output; fall back to text otherwise.

The HTTP variant is stateless per MCP 2026-07-28 (serve mcp --http, default 127.0.0.1:8081): POST-only at path-agnostic endpoints (/ and /mcp both answer), SSE-wrapped responses, notifications acknowledged with a bare 202, no Mcp-Session-Id issued, GET/DELETE → 405. --auth-token is required for non-loopback binds unless --insecure-no-auth.

Verified live (2026-11-13, v1.153.0 — ex05 README): node .\probe-mcp.mjs asserted serverInfo {"name":"docker agent","version":"v1.153.0"}, protocolVersion 2025-06-18, the single root tool with the agent.yaml description, and tools/call of "Reply with the single word: pong" → structuredContent: {"response":"pong"} — ~20 s end to end. Claude Code 2.1.101 connected live (claude mcp add ex05-agent -- docker agent serve mcp … → ✓ Connected). The probe's own red lesson: serve mcp rejects --session-db (unknown flag) — pin the global --data-dir to a throwaway dir instead.

serve a2a — your agent is a discoverable peer (ex06)

Discovery. GET /.well-known/agent-card.json returns an A2A v1.0 card: it names the interface ({"url":"…/invoke","protocolBinding":"JSONRPC","protocolVersion":"1.0"}), advertises capabilities.streaming:true (unexercised here), auto-generates skills[0] with tags ["llm","docker agent"], and its version is the serving CLI version, not a config field. The legacy /.well-known/agent.json is dead → 404 (re-verified on v1.153.0) — old-bookmark tooling looks "deployed" while discovering nothing.

CamelCase methods only. This build embeds A2A v1.0: SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask, SubscribeToTask, GetExtendedAgentCard. The v0.2-style message/send is rejected, as are message:send, send_message and invoke — sending a message IS SendMessage.

One SendMessage returns a whole task object, not a string: status.state → TASK_STATE_COMPLETED, history[] echoing the user message, artifacts[] carrying the answer, contextId tying the conversation, metadata showing cagent's google-ADK extension (adk_app_name = the config filename). An answer to forward, not just text to display.

# Read the LAST artifact — the FIRST one is cosmetic:
#   artifacts[0]     → metadata {adk_partial: true}, parts [{data:{}, …}]   ← no text, ignore it
#   artifacts[last]  → parts [{text: "A2A OK"}]                             ← the answer
# Verbatim fields from the observed task response: status.state = TASK_STATE_COMPLETED
# (timestamp 2026-11-13T06:08:44.2329583-08:00), contextId = 01a1d53d-4182-760f-8c22-0d63287da1eb,
# metadata = {adk_app_name: "agent", adk_session_id: "…", adk_user_id: "A2A_USER_…"}

Verified (2026-11-13, v1.153.0 — ex06 README): round trips 331 ms / 496 ms; artifact text exactly "A2A OK"; the card says "name":"agent" while the agent block is named root — the card name is the config file's stem, not the agent name (-a/--agent does not change it). Between v1.145.0 and v1.153.0 the card grew capabilities.pushNotifications:false — script against field presence and meaning, not exact snapshots.

serve acp — your agent is an editor citizen (ex07)

stdio only, and the only serve surface with no flags at all — no --listen, --http, --safety or --auth (observed on both plugin versions): an ACP host (an editor such as Zed) spawns the agent as a subprocess and drives it over JSON-RPC 2.0 NDJSON with a session lifecycle and streamed updates — the same shape as LSP/DAP integrations. Docker Agent speaks ACP v1 (the stable line; v2 exists only as Draft).

The handshake, machine-verified on the wire (2026-11-13, v1.153.0 — ex07 README):

  1. initialize with protocolVersion: 1 → negotiates the number 1 (send the number, not the string "1"), agentInfo: "docker agent v1.153.0", authMethods: ["host-credentials"] — no interactive auth, because the config names its ollama model provider.
  2. session/new → a real sessionId (UUID) plus cagent configOptions: the editor can switch the tool-safety mode (default|strict|balanced|restricted|autonomous) and the per-agent model from inside its UI, mid-session — the local↔cloud swap surfaces as data, not a flag.
  3. session/prompt → streamed session/update notifications (available_commands_update, config_option_update, current_mode_update, agent_message_chunk) → resolves with {stopReason: "end_turn"}. Observed round trip: exactly {"type":"text","text":"pong"}, messageChunks=1, thoughtChunks=0.

The envelope-shape lesson (the probe's red→green story). v1.145.0 carried update notifications flat on the params (params.sessionUpdate + params.content); v1.153.0 wraps them in an envelope — params.update.{sessionUpdate, content, …} — and adds new kinds. The first probe run was red: the reply pong was already on the wire while the probe read the wrong envelope — a client pinned to the flat shape sees the reply bytes but reads none of them. Parse both shapes.

Editor steps carry the UNVERIFIED-ON-THIS-MACHINE label. No ACP host was installed on this machine, so the Zed walkthrough (Agent Settings → External Agents → Add Custom Agent; an agent_servers entry whose command is "docker" with args including agent, serve, acp plus the absolute config path — quoted verbatim from Zed's external-agents documentation as captured in the exploration notes) is the owner demo. VS Code 1.143.1 does not speak ACP (third-party host extensions are documented; none installed or attempted). Claude Code 2.1.101 is an MCP client, not an ACP host. For your own runs: local models stream thoughts — gemma4 can emit about a minute of agent_thought_chunk before the first agent_message_chunk; render chunks by their sessionUpdate kind or a waiting client looks hung while the model thinks.

The honest rows — and the shared machinery underneath

serve api (default 127.0.0.1:8080) — session-based REST (POST /api/sessions) — and serve chat (default 127.0.0.1:8083) — OpenAI-compatible chat completions — are documented from --help text and the port map and never probed (the phase's label: "documented surfaces, unverified on this machine," flavors.md). OCI share (docker agent share push|pull) is out of scope this phase — it needs a registry.

Shared behavior, observed on every probed surface. The startup banner declares the policy:

Tool safety policy: restricted (source: serve default)

…stdout carries protocol NDJSON only (all logging on stderr — the split that makes standard SDK stdio transports work untouched), and on Windows cleanup must kill the process tree: the listener is the docker-agent.exe child of the docker wrapper — wrapper-kill can orphan it with the port squatted.

taskkill /pid <pid> /T /F

The probes made the gotcha an assertion: ex06's kills the tree (with a netstat -ano fallback to the port owner) and proves the port re-binds before exiting 0 — a leaked tree fails the run instead of haunting the next one; 8081 stays occupied until the tree is gone.

The config stays declarative — and deliberately tool-free

ex05/ex06/ex07's agent.yaml keeps the ex01 shape (a named gemma4_local entry on the built-in ollama provider) with no toolsets — on purpose. From ex05's config comment: "this round trip needs no tools at all, and a tool-free agent never runs into serve's default restricted tool-safety mode." ACP goes further: an editor brings capabilities with it — fs reads/writes and terminal access arrive through the client's clientCapabilities and session/request_permission, not agent-side toolsets.

Add toolsets to a served agent and you inherit the fail-closed behavior Ex02 documented (restricted denies unattended calls); ex06's README adds the escape — tasks that must write or run commands need --safety autonomous on the serve command, a deliberate one-shot with the blast radius read first.

The version lesson across the family (v1.145.0 → v1.153.0 auto-update mid-phase): MCP initialize dropped the logging:{} capability; the A2A card gained capabilities.pushNotifications:false; ACP updates gained the envelope. Core surfaces proved stable.

03Judge the wire — three surfaces, three verdicts

The Lesson 002 skill, one layer out: the transcript is now a protocol exchange, and exit codes still lie — the repo's serve probes assert the wire itself (handshake fields, round-trip payload, task state, port re-bound) precisely because the serve process's exit code is not trusted. Answers lock in once chosen.

Case A — the snake_case caller

Your A2A client POSTs to /invoke with "method":"message/send" (the v0.2-era name from an old tutorial). The server answers, verbatim shape:

{"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"method not found","data":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","domain":"a2a-protocol.org","reason":"METHOD_NOT_FOUND"}]}}
-32601 is "method not found", and this build speaks A2A v1.0 with CamelCase methods only. The ex06 README records that message/send, message:send, send_message and invoke are all rejected with -32601 (observed live in the exploration notes and re-verified on v1.153.0). The correct method is SendMessage — this is not a server misconfiguration; it is a naming bug in your client.

Case B — the artifact that came up empty

A consuming integration reads artifacts[0].parts[0].text to display the answer. The task reads TASK_STATE_COMPLETED and the artifacts array is non-empty — but the text is empty. The task object did arrive; the serve process is healthy.

The ex06 README gotcha, verbatim in spirit: a cosmetic first artifact (metadata adk_partial:true, empty data) precedes the real answer — consuming code that grabs artifacts[0] gets nothing; take the last artifact that has parts[].text. On the verified run the answer "A2A OK" lived in artifacts[1] while artifacts[0] carried the adk_partial marker with no text at all.

Case C — the reassuring annotation

In a design review someone reads tools/list from your served agent and points at readOnlyHint: true: "My data is safe — the tool declares itself read-only. And with serve defaulting to restricted, anything it didn't like would be routed to a human for approval before running."

Two claims, both wrong. One: annotations are generic, not semantic (ex05 README) — readOnlyHint:true was observed even though a call runs a full LLM chat; an agent with write toolsets would still act. Two: restricted is fail-closed — the mode's fallback denies instead of asking for confirmation (Ex02's exact denial text). What keeps ex05's round trip safe is that the committed config declares no toolsets at all: nothing to approve, nothing to deny.
Where each verdict comes from: Case A — ex06 README "Method casing" gotcha; Case B — ex06 README "Read the LAST artifact" gotcha; Case C — ex05 README "Annotations are generic" + the serve-default restricted note. All observed 2026-11-13 on docker agent v1.153.0.

04Carry forward

  1. Roles before protocols. Work that splits into roles → sub_agents: first: an array of sibling entry names under the lead, lead-only transfer_task ({agent, task, expected_output}), sub-answers back as tool-result data, reviewer starting from a fresh view. But plan for the fan-out: one task ≈ 5 model chats, bounded only by per-agent max_iterations: (12 / 6 / 6 in ex04) — which is why ex04 ships on glm-5.3-flash:cloud.
  2. One verb, five seats. docker agent serve <mode>: mcp (tool seat — stdio default, --http becomes stateless 8081), a2a (peer seat — 8082, card + task lifecycle), acp (editor seat — stdio, no launch flags at all), plus api (8080) and chat (8083) — those two documented, never probed.
  3. Dress the wire for its reader. MCP: one tool per agent, named after it, described by the agent's description: field — annotations are generic, not semantic. A2A: CamelCase SendMessage, card at /.well-known/agent-card.json, read the LAST artifact. ACP: negotiate the number 1, stream session/update, tolerate both envelope shapes.
  4. Serving defaults to restricted — safe only because the configs are tool-free. The banner says so (source: serve default); add toolsets and unattended calls fail closed. stdout = protocol NDJSON only, stderr = logs; on Windows kill the tree, not the wrapper.
  5. The probe's exit code is trustworthy by construction. It asserts the protocol surface and never trusts the serve process's own exit code — then taskkill /pid <pid> /T /Fs the tree and, in ex06, proves the port re-binds before calling it green.
