01The decision path — read it in order

flavors.md answers which connection do I want, and when; run-modes.md answers how do I run it. The repo's decision rules are an ordered list, and the order is a cost argument: structural before protocol, borrowed before built. Six questions, six answers.

  1. Does the work split into ROLES — plan / review / compose? → Native sub_agents:, reach it first, before any networking setup: zero protocol chatter, one YAML file — the list hands the lead a transfer_task tool. Accept the cost: of the built-in options this one is the priciest — one task fans out into ~5 model chats.
  2. Need a capability you DON'T own — proven tools like web search, no budget for code? → Catalog MCP ref (type: mcp, ref: docker:…): the fastest off-the-shelf path — the ref plus Docker's catalog snapshot is the server. Bounded by the catalog; keyed entries need secrets, out of scope in the no-secrets phase.
  3. Need a tool you DO own and can test — exact, a repo artifact? → Custom MCP server (type: mcp, command: docker run --rm -i <img>): you build and tag the image; a fresh container per session with --rm cleanup; same behavior every time. How it connects follows how it starts: a command: spawn talks over stdin/stdout, one JSON line at a time.
  4. Should someone else's MCP CLIENT call YOUR AGENT as one tool? → serve mcp: one tool per agent, named after the agent; the agent's description: steers the caller; no config change — the same YAML, one serve verb.
  5. Should another AGENT discover and consume yours over HTTP? → serve a2a: an agent card at /.well-known/agent-card.json; one SendMessage returns a whole task object (TASK_STATE_COMPLETED + artifacts); CamelCase A2A v1.0 methods.
  6. Should the HUMAN's EDITOR drive your agent? → serve acp: stdio-only, no launch flags — the editor starts it like a language server; file and terminal abilities arrive through the editor's clientCapabilities and session/request_permission prompts, not agent-side toolsets.

The one-line mental model — keep all four lines in your head

MCP wires tools into an agent (or the agent out as one tool); A2A delegates work between agents over a network, with discovery; sub_agents is multi-role work inside one config; ACP is the editor-facing seat — the human's tool is the peer.

03The trade-off ledger — and the honesty list

The flavor sheet's cost column is the honest part of its table; the phase notes sharpen it. Before the drills commit you anywhere, read what each choice gives up — not disqualifications, just price tags you accept with it.

🧮 sub_agents — you pay in model chats

One task fans into ~5 model chats (lead turns + a full nested chat per sub-agent); hence Ex04's cloud default, glm-5.3-flash:cloud, the one-line local swap for cheap iteration, and per-agent max_iterations kept small (shipped split: lead 12 / subs 6). Isolation is real but inside one program: sub-agents see only what the lead forwards. The proof is transcript lines (transfer_task response), not a protocol check — there is no protocol.

📦 Catalog ref — you pay in pin stability and egress

The ref carries no version: a newer catalog snapshot can swap the exact image — and change the tool with it. Each call fetches a container that may talk to only one web address (~40 s first call). You're limited to what the catalog holds; key-required entries (brave, tavily, exa) need secrets — Ex02 chose DuckDuckGo to stay key-free. And MCP calls aren't on the clearly-safe list: under restricted they are refused, so unattended verification runs use a deliberate --safety autonomous one-shot.

🔨 Custom MCP server — you pay in artifact ownership

Server code + Dockerfile + image upkeep are yours: one-time 172 MB build on node:24-alpine, image stays until docker rmi. Stdio discipline: stdout pure one-JSON-per-line, stderr the log channel. A missing image fails almost silently and still exits 0 — debug toolsets is the model-free check. Same safety row as any MCP call: refused under restricted.

🧰 serve mcp — you pay in description-only steering

The caller steers by your description: alone; annotations are generic (readOnlyHint: true despite a full LLM chat — don't read safety into them). One full LLM chat per tools/call (~20 s local gemma4). Serving defaults to restricted tool safety (Tool safety policy: restricted (source: serve default) — observed live in Ex05/Ex06), comfortable only because those configs declare no toolsets; a served agent with toolsets inherits the same refuse-by-default denials. The stdio variant accepts no --safety/--auth-token; those exist only on the session-less --http variant (default 127.0.0.1:8081, auth required for non-loopback binds).

🌐 serve a2a — you pay in protocol surface

There's no one to negotiate discovery/protocol drift with but yourself: the CLI moved v1.145.0 → v1.153.0 and the card grew capabilities.pushNotifications:false. This build speaks A2A v1.0 with CamelCase methods only (older snake_case names like message/send answer -32601); legacy agent.json discovery is 404; the card's name is the config file's stem, not the agent name. Serving itself is free — one LLM round trip per task: 331–496 ms overhead beyond the model on this build.

💻 serve acp — you pay in host dependency

The editor, not your config, brings file/terminal abilities (clientCapabilities + session/request_permission prompts) — the example config deliberately carries no toolsets. The host must speak ACP v1 (protocolVersion: 1 — the number; v2 only Draft). The wire moved between plugin versions — update notifications grew an envelope, and a client pinned to the flat shape reads none of it (how Ex07's first probe run went red). gemma4 streams its thinking: ~1 min of agent_thought_chunk before the answer — keep the UI streaming. The in-editor session is the owner demo: no ACP host was installed on this machine — editor steps stay UNVERIFIED-ON-THIS-MACHINE.

⚠ Environment honesty — costs you cannot see in any one row

One model server, shared waiting. Every timing number in this course was measured while no runs overlapped; overlapping runs queue up on the same model server/GPU and stretch everyone's wall time (phase notes §1).

Exit 0 is not success — everywhere. Refused tool calls (Ex01–03), missing tool images (Ex03) and stuck tool loops (Ex01/02) all still exit 0. Serve surfaces change the proof's shape: their probes check the protocol messages themselves, so the probe's exit is trustworthy by design. One-sentence form (run-modes.md §9): exit 0 means the agent finished, not that the task succeeded.

The CLI already changed once under this course (v1.145.0 → v1.153.0): MCP initialize dropped the logging:{} capability; ACP update notifications grew an envelope; the A2A card grew a field. Script against what a field means being present, not exact snapshots.

And on Windows: PowerShell 5.1 mangles embedded double quotes in --exec text; serve spawns a child docker-agent.exe that holds the listener — kill the tree (taskkill /pid <pid> /T /F), not just the wrapper (Ex05–Ex07).

🚧 The honesty list — documented, not built this phase

None of these was exercised by an example this phase:

• Headless CLI (run --exec, --json, stdin) — not a connection type but the run mode every example's automatic check uses: a one-shot headless run.

• serve api — default 127.0.0.1:8080. Session-based REST (POST /api/sessions, --auth-token bearer, --session-workingdir-root for multi-user scoping). Documented from --help text; never probed.

• serve chat — default 127.0.0.1:8083. OpenAI-compatible chat completions over the agent. Documented from the port map; never probed.

• OCI share (docker agent share push / pull) — an agent config shared as an OCI artifact; sub_agents: and serve doors accept OCI references directly. Out of scope this phase (needs a registry); closest verified behavior: a non-path argument to run is parsed as a registry reference.

Those last three carry the honest label — documented as surfaces the CLI exposes, unverified on this machine — a next step for the owner if a use case needs them.

Five lines to keep

  1. The decision path is ordered. Roles → sub_agents first; capability you don't own → catalog ref; tool you own and can test → custom MCP server; someone's MCP client calls your agent → serve mcp; another agent over HTTP → serve a2a; the human's editor → serve acp.
  2. The comparison table is the syllabus. One row per flavor — isolation, cost, complexity, when-to-reach. When two rows both fit, the row you pick is the trade-off you accept.
  3. Flavors stack — toolsets inside an agent that also declares sub_agents: is composed YAML (a reading of the docs' structure; no example ran a stack end to end).
  4. Judgment needs evidence: exit 0 (or a probe's exit) plus something you can point at — transcript lines, protocol checks, or a real side effect; write code against what fields mean, not exact snapshots — the CLI already changed once.
  5. serve api, serve chat and OCI share stay on the honesty list — documented, unverified on this machine. The deliberate pause ends the phase; the first real problem is the owner's move.
