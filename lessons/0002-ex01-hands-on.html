Ex01 hands-on — run it, then judge it

Lesson 001 gave you the mental model. Today you drive ex01-first-agent for real: four pre-flight gates, a free dry-run, the TUI demo, then the repo's verification template — and the judgment call that exit codes cannot make for you.

ex01-first-agent you type the commands ~30 min Windows 11 · PowerShell 5.1 prereq: Docker Desktop + Ollama installed

01Four gates before any spend

Most broken runs trace back to a check that was skipped. These four take under thirty seconds combined, and two of them are free — they never touch a model. Tick each one as you run its command; your ticks persist in this browser.

① Docker Desktop is running

You need the engine (the Server section in the output), not just a client build.

docker version

② Ollama daemon is up, and the model is present

Required for every run of ex01 — local and cloud alike. The built-in ollama provider talks to localhost:11434. The list must show gemma4:latest (glm-5.3-flash:cloud is optional, for the cloud path only).

ollama list

③ The CLI plugin answers — and you can read a health report

docker agent doctor is the one-shot health check. On this machine it exits non-zero because Docker Model Runner is unreachable — that is not a blocker for ex01, which pins the ollama provider and never touches Model Runner.

docker agent doctor

④ Config sanity — the free gate

--dry-run validates the config without touching a model. Later examples in this repo run this same gate before any spend.

cd ex01-first-agent; docker agent run .\agent.yaml --dry-run
✓ All four gates green — you're spend-safe. Continue to Part 02.

⚠ Why gates ② and ③ look contradictory — they aren't

Gate ② must be green before any run (the daemon serves every model call), while gate ③ may end non-zero and still be fine (its only complaint here is Model Runner, which ex01 never uses). If a run later misbehaves, the README's first diagnostic reflex is ollama list — the daemon explains far more failures than anything else on this box.

02Two surfaces: look around, then verify

The chat window is for looking around; the verification command is for proof. Ex01 is verified through exactly one command — the same shape every later example in this repo reuses. Run the chat once to loosen up, then switch to the command.

TUI — owner demo (interactive; nothing is asserted)

cd ex01-first-agent
docker agent run .\agent.yaml

Chat freely: ask what tools it has, or what it can read. Quit with Ctrl+C. Nothing here is checked or stored — this surface exists so you've seen the agent think.

The verification template — ex01's one machine-checked command

docker agent run .\agent.yaml --exec 'Read agent.yaml in the current directory using your filesystem tools. Then answer with exactly two lines. Line 1: the provider and the model name you find under models. Line 2: the three toolset types listed for this agent.' --safety restricted
PieceWhat it doesWhy it earns its place
docker agent run .\agent.yaml Config file first, as the positional argument. The config is the program — and the command doesn't guess filenames (only docker-agent.yaml would be found automatically), so type it.
--exec '…' One-shot run with no chat window: it does the task, prints the full transcript, then exits. A scripted run is itself the test — the transcript is the evidence.
the task wording Read-only, narrow, and the answer lives entirely inside a file the agent must read. Reliable for a small model; same result every time; leaves no scratch files.
--safety restricted Made for runs with nobody watching: safe calls pass on their own, everything else quietly refused, no human prompted mid-run. This read-only task passes unattended; nothing risky slips through.

Shape of a passing run (abridged — not literal output)

# tool calls:  read_file(agent.yaml)          → agent reads the file
# final answer (two lines):
ollama gemma4:latest
filesystem shell think
# exit code: 0

🚦 Exit 0 is the start of judgment, not the end

A denied tool call still exits 0 — the denial exists only as a transcript line, e.g. Tool 'write_file' is denied by the restricted safety mode…. That's why the repo judges every verification run on exit code plus transcript content. When you write automated checks later, check the answer lines — never the exit code alone.

⚠ PowerShell 5.1 notes for these commands

Single quotes are literal — use them for the --exec task (as above). Use ;, not &&, to chain commands. If the task text ever contains double quotes that PS mangles when you paste, shift the task onto stdin instead:

echo '<the same task text>' | docker agent run .\agent.yaml - --exec --safety restricted

The - argument says "read the message from stdin". Ground truth: the repo's run-modes notes verified this form.

🧪 Optional awareness — the one-line cloud swap (your spend, already smoke-verified once)

The config's swap point is a single value: model: gemma4:latest → model: glm-5.3-flash:cloud (same daemon, proxies to Ollama Cloud; requires the Ollama app signed in). A minimal --exec 'Reply with the single word: pong' smoke returned pong on 2026-10-19 for well under one cent. Whether the full verification template behaves identically on the cloud model was never tested — treat that as unknown. The committed config stays on the local model; rerun anything cloud-side only if you decide it's worth the spend.

03Judge the run — the skill that transfers

The repo's contract for every verification run in this sequence: exit 0 and the two correct lines in the transcript. Both halves. Here's what passing looks like, then three real transcripts for you to judge — pick a verdict for each.

The verified passing run, annotated (recorded 2026-10-19, docker agent v1.145.0)

# … first tool call reads the file — with a stumble:
read_file(agent.yaml, limit: 0)
# → tool error: invalid limit 0: limit must be >= 1
# … the agent read the error and retried with a valid limit:
read_file(agent.yaml, limit: 200)          ← self-correction, not a failure
# … final answer, exactly two lines:
ollama gemma4:latest
filesystem shell think
# exit code: 0

That limit: 0 stumble is in the verified-run record. The tool error was clear enough that gemma4 fixed itself on the retry — self-correction in a transcript is healthy behavior, not noise. The real danger is the opposite: a run that looks fine from the exit code while the transcript records denials you never saw.

🎯 Practice: judge each transcript

For each simulated run, pick the verdict. Answers lock in once chosen — like the quiz.

Case A — a plain verification run

Exit code 0. Transcript: a read_file on agent.yaml (after one self-corrected limit: 0 error), then the two lines — ollama gemma4:latest and filesystem shell think — then clean exit.

This is both halves of the contract: exit 0 and the exact two expected lines. The retried read_file is healthy self-correction — small models stumble; the transcript shows they recovered. Verdict: pass.

Case B — a task that wanted to write

Exit code 0. Transcript: the agent calls write_file, gets Tool 'write_file' is denied by the restricted safety mode…, retries the identical call several times (detected 5 consecutive identical calls), then answers with a vague summary and exits.

Classic hidden failure. The refusal exists only in the transcript; exit 0 lied. Under --safety restricted the refusal itself is correct behavior for a run with nobody watching — the mistake was designing a verification task that must write. Make the task read-only, or deliberately approve the write with autonomous/--yolo if you mean it. Note the small-model loop too: five identical refused calls before giving up.

Case C — the message came first

You paste docker agent run "hello world" --exec in PowerShell. Output: Error: could not parse reference: … hello world. No transcript, no tool calls at all.

Setup problem, caught before any model spend. The first positional argument is the config, not the message — Docker Agent tried to parse "hello world" as a registry reference. Fix: put the file first (docker agent run .\agent.yaml "hello world" --exec) or pipe the message on stdin (echo "hello world" | docker agent run .\agent.yaml - --exec). Recorded in the repo's run-modes gotchas.

🧰 When your real run misbehaves — check in this order

  1. Reread the transcript. Denials, loops, and wrong answers live there; exit codes rarely tell the truth on their own.
  2. ollama list. Daemon up? Model present? Most failures on this box stop here.
  3. docker agent debug toolsets .\agent.yaml. The exact tool list — looking it up catches a missing toolset that "feels" like a run bug.
  4. Narrow the task. Read-only, one file, a two-line answer — reliability for a small model is a task-design skill, not a magic phrase.

04Carry forward

  1. Four gates, every time — Docker Desktop, ollama list, the plugin's health report (a Model-Runner complaint is expected and fine here), and --dry-run. Under thirty seconds.
  2. The template is one command — config first, --exec '<task>', --safety restricted — and every later example in this repo reuses exactly this shape. Learn it once here.
  3. Exit 0 starts the judgment; the transcript finishes it. Refused calls and tool loops leave the exit code untouched — the transcript is where failure actually lives.
  4. The two lines are the pass marker — ollama gemma4:latest, then filesystem shell think. Assert on content, never on exit code alone.
  5. Self-correction is healthy; silent refusals are the danger. Read every transcript before you believe anything — including your own runs.
