Lesson 003 · The MCP flavors — catalog ref vs your own server

Lesson 002 had you run and judge Ex01. Now the same agent reaches outside itself through MCP: two verified examples do the same job — being an MCP client — by two routes: Docker's ready-made catalog tool with zero server code (ex02), and your own ~100-line server in a container (ex03). Plus the safety-mode switch, the cost-free check, and the transcript traps both leave behind.

ex02-mcp-catalog-tool ex03-mcp-custom-server ~35 min Windows 11 · PowerShell 5.1 prereq: Docker Desktop + Ollama (+ docker build for ex03)

01Same seat, two entrances — MCP as client

An agent that uses outside tools is an MCP client. Ex02 and Ex03 do the same job; what differs is who supplies the tool. Exactly one new toolset type enters the config — type: mcp — and both committed configs differ from Ex01 by roughly this one entry.

Grounding: run-modes.md §14 counts 27 built-in toolset types; Ex01 used three of them (filesystem, shell, think — expanding to 11 concrete tools). The full list also includes mcp_catalog — the gateway machinery behind catalog entries (docker agent toolsets shows it) — but what actually goes into an agent config is a plain type: mcp entry. Here are the two real toolsets, verbatim from each agent.yaml:

ex02 — MCP by reference to Docker's catalog

toolsets:
  - type: filesystem
    allow_list:
      - "."
  - type: think
  - type: mcp
    ref: docker:duckduckgo   # containerized "Private Web Search" server from Docker's MCP catalog
    tools:
      - search

ex03 — MCP by command: the agent spawns your own containerized server

toolsets:
  - type: filesystem
    allow_list:
      - "."
  - type: think
  - type: mcp
    command: docker      # the agent spawns this command itself; MCP over stdio
    args:
      - run
      - --rm
      - -i
      - mcp-ex03-echo:local   # built by the README's docker build command
    tools:               # allowlist: expose only the one tool this server has
      - echo

What the catalog entrance provides — version-locked and key-free

docker:duckduckgo resolves to Private Web Search (community-maintained, not affiliated with DuckDuckGo): image mcp/duckduckgo@sha256:5617c4c60f48f47556c0735de7a73f6abd731c132c65ec8c720b511819c9f88f with egress restricted to html.duckduckgo.com:443 — allowed to talk only to that one web address (observed at this machine's 2026-10-25 catalog snapshot — ex02 README). The first MCP call starts the MCP gateway and auto-pulls that image; nothing needs to be installed or configured locally. Browse the catalog with docker mcp catalog ls.

DuckDuckGo was chosen over the catalog's brave/tavily/exa search entries precisely because it needs no API key — the phase's no-secrets rule stays unbroken. What this route costs: the first call took ~40s (gateway start + image pull); reruns finish in well under a minute.

What the custom entrance provides — a server you can read

MCP over stdio is just text messages — one JSON line at a time, over standard input and output — and writing one tiny server teaches you the whole thing. server.ts handles initialize (echo back a protocolVersion + serverInfo), notifications/initialized (a notification — no response may be sent), tools/list, tools/call, and ping — that whole protocol surface is ~100 lines with no SDK.

The tool description is a prompt to the model. inputSchema (message, required) tells the runtime which arguments to enforce, while the description text — Echoes back the given message prefixed with ECHO:, plus the character count — is what actually guides how the model calls the tool. Write that description as if you were prompting the model — because you are.

How it connects follows how it starts. The agent starts the server as its own child process (command: docker, args: [run, --rm, -i, <image>]), so the messages travel over stdin/stdout — not a network address. Keep stdout strictly one JSON line at a time — anything else corrupts the protocol stream; stderr stays free for server logs (the ready on stdio banner lives there).

Note there is no image: key, and no URL-style consumption for local servers — docker run in command/args is the containerization path.

The inline shape vs the named shape

Ex03 uses the inline shape (type: mcp + command:/args: on the agent). An equivalent alternative — same debug toolsets output, proven during this machine's exploration (ex03 README) — is a top-level named block plus a reference:

mcps:
  echo-srv:
    command: docker
    args: [run, --rm, -i, mcp-ex03-echo:local]
agents:
  root:
    toolsets:
      - type: mcp
        ref: echo-srv

Inline is chosen in ex03 because it keeps one agent's wiring next to that agent; the named shape pays off once several agents share one server definition.

02Why the safety mode flips to autonomous

Ex01's verification ran --safety restricted because its read-only calls count as safe. Here that stops working: MCP calls — catalog or custom — are not on the clearly-safe list (cross-flavor caution in flavors.md). That one fact changes the safety mode in the template; each example's mode was tested with real runs before committing, not assumed (phase-notes §3).

The recorded proof — same mode, two flavors, one denial text

Under --safety restricted, both examples' tool calls were auto-denied in the transcript. That is correct refuse-by-default behavior — in a run with nobody watching, there is nobody to approve anything:

# ex02, catalog tool (Tool approvals — ex02 README):
Tool 'search' is denied by the restricted safety mode: the call is not
classified safe, and the mode's fallback denies instead of asking for confirmation.

# ex03, your own container (Tool approvals — ex03 README):
Tool 'echo' is denied by the restricted safety mode: the call is not
classified safe, and the mode's fallback denies instead of asking for confirmation.

After the denial, ex02's transcript showed search response → "Tool 'search' is denied…" and gemma4 correctly answered that it could not search — with exit 0. Same verdict either way: who serves the tool (a catalog gateway or your own container) does not change how it's classified. The same caution's contrast: delegation (transfer_task, Ex04) is classified safe, so its template keeps restricted.

Why not balanced — and why autonomous is deliberate

run-modes.md §11 — --safety <mode> controls who approves tool calls:

ModeBehaviourUse for
strictask for everythinginteractive exploration
balancedauto-approve safe calls, ask for the restinteractive with a light touch
restrictedauto-approve safe calls, deny the restunattended / CI
autonomousapprove everythingdeliberate one-shot commands

--yolo is an alias for --safety autonomous. Balanced would be worse than restricted here: with no human present, the pending call surfaces as The user rejected the tool call. (ex02 README + run-modes §11 — observed). autonomous auto-approves everything and stays reserved for deliberate one-shot commands where you have first read everything they're allowed to do. The rule this phase settled on: restricted when the task's calls are safe-classified (Ex01, Ex04), autonomous one-shots when the point of the example is a call that is not (Ex02, Ex03) — never balanced unattended.

The model-free check — before any model spend

docker agent debug toolsets .\agent.yaml expands the config into the exact tool list the model would see — 11 tools for both configs here: 9 filesystem + think + the one MCP tool — and it actually starts the toolsets (phase-notes §7), so a working catalog entry or a built image shows its tool, while a missing one simply doesn't appear. For ex02 it's quick proof that the ref pointed at the right server; for ex03 it's the check that was learned from the missing-image mistake.

docker agent debug toolsets .\agent.yaml

⚠ The missing-image trap (ex03)

Run ex03 without docker build and nothing screams. debug toolsets printed the usual filesystem/think tools with no echo — exit 0. A real headless run printed ⚠️ Some toolsets failed to initialize for agent 'root' plus mcp(stdio cmd=docker ...) start failed: failed to initialize MCP client: connection closed: calling "initialize": client is closing: EOF the container exits instantly, so the MCP handshake hits an unexpected end-of-file (EOF) — and still exited 0 while gemma4 answered honestly that the tool was unavailable.

Worse: small models can believe they called the missing tool — gemma4 reasoned "I executed the echo tool" while the only real echo line in the transcript was echo response → "Tool 'echo' is not available…". Judge tool usage by the response → transcript lines, never by the model's narrative (ex03 README gotchas).

The red run also showed the default resilient behavior: the agent keeps running in a reduced state and loops on the unavailable tool rather than refusing to start. A lifecycle: {profile: strict} refuse-to-start option exists in the schema but is deliberately left unverified on this machine.

The gate sequence for ex03 — in this order

cd ex03-mcp-custom-server
docker build -t mcp-ex03-echo:local .

Puts server.ts into a node:24-alpine image (172 MB; Node v24.22.3 — the version that runs a .ts file directly). Needs no running model or Ollama. Verified against docker agent v1.153.0 (Docker Engine 29.9.3), 2026-11-13 — ex03 README.

docker agent debug toolsets .\agent.yaml

Green means 11 tools for this config, with + echo - Echoes back the given message… among them. That line is the gate: a list of 10 (no echo) means the image is missing, whatever else a later run may claim.

The verification templates (headless — machine-verified; same shape as Ex01, different mode)

# ex02 — from ex02-mcp-catalog-tool/
docker agent run .\agent.yaml --exec 'Use your web-search MCP tool: search the web for Docker MCP Gateway GitHub repository. Then answer with exactly two lines. Line 1: the URL of the official GitHub repository from your search results. Line 2: the exact title shown for the top result.' --safety autonomous

Task design (ex02 README): the two answer lines can only exist if the search tool really ran — a small model can't reliably guess the exact title offline. The wording avoids double quotes, which PowerShell 5.1 mangles inside --exec text (same gotcha as Ex01). The catalog's snapshot also fixes the tool's interface — search takes query, max_results (1–20, default 10), optional region; gemma4 chose max_results: 1 unprompted.

# ex03 — from ex03-mcp-custom-server/
docker agent run .\agent.yaml --exec 'Use the echo tool from your custom MCP server to echo exactly this text: round trip check 42. Then answer with exactly two lines. Line 1: the exact text the echo tool returned. Line 2: the character count it reported.' --safety autonomous

Task design (ex03 README): both answer lines can only come from the tool round trip — the ECHO: prefix and the character count (round trip check 42 = 19 chars) are computed inside the container by server.ts.

Optional awareness — the one-line model swap (README wording, no new advice)

Identical to Ex01/Ex02 — swap one line in the named models entry: model: gemma4:latest → glm-5.3-flash:cloud (same daemon proxies to Ollama Cloud); the cloud swap additionally needs the Ollama app signed in. The MCP toolset is model-agnostic: the same catalog ref / spawned server works unchanged under whichever model drives the tool calls, and the cloud model is the better tool-caller for multi-step chains. The committed configs stay on local gemma4.

03Judge the transcript

The contract hasn't changed since Ex01: exit 0 and transcript content — both halves. What MCP adds is a bigger collection of failure shapes: a refused call that exits 0, a missing image that exits 0, and a model that can claim it made a call the system rejected. Three real recorded situations follow — pick the verdict for each. Answers lock once chosen, like the quiz.

Case A — the round trip that proves the server (ex03)

You ran ex03's verification template with --safety autonomous. Exit 0, run under a minute. Transcript: Calling echo(message: "round trip check 42"), then echo response → "ECHO: round trip check 42 (19 chars)", then the final two lines quoting the exact returned text and its character count.

Both halves of the contract: exit 0 and a response line whose ECHO: prefix and 19-char count could only have been computed inside the container by server.ts — a model cannot guess them (ex03 README: both answer lines can only come from the tool round trip). Observed 2026-11-13, docker agent v1.153.0. The transcript doubles as proof the container was spawned, handshaken, and called.

Case B — the denial that still exits 0 (ex02)

You tried ex02's catalog verification under --safety restricted for an unattended CI-style run. Exit 0. Transcript: search response → "Tool 'search' is denied by the restricted safety mode…"; gemma4 replies plainly that it could not search.

Not success — the failure hides only in the transcript; the exit code lied. The refusal itself is correct refuse-by-default behavior: nobody is there to approve, and MCP calls are not on the clearly-safe list (flavors.md cross-flavor caution; the exact refusal line is in the ex02 README — and the verdict is identical for ex03's custom echo: who serves the tool does not change the classification). Under balanced it would instead read The user rejected the tool call. — autonomous is the deliberate one-shot this template reserves. For CI: exit 0 is not enough; check transcript and answer content.

Case C — the believed call (ex03)

You skip docker build and run anyway. Exit 0. Transcript: ⚠️ Some toolsets failed to initialize for agent 'root' plus the initialize handshake closing with EOF; the model's reasoning narrates "I executed the echo tool", yet the only echo line reads echo response → "Tool 'echo' is not available…".

Setup problem — and you paid for it anyway. The image does not exist; the container exits instantly and the handshake reads EOF, while the run exits 0 and the model's reasoning believes a call the framework rejected. Only the response → transcript line is truth (ex03 README gotchas; the recorded run even had gemma4 answering honestly that the tool was unavailable — but its reasoning narrated the phantom call). Fix: docker build -t mcp-ex03-echo:local . first, then the model-free check — debug toolsets must list 11 tools with + echo among them.

04Carry forward

  1. One new type, two entrances. type: mcp is the only new toolset type — ref: docker:duckduckgo (ex02) and your own command:/args: (ex03) occupy the identical MCP-client seat; the named-block shape (mcps: + ref:) is the equivalent write-up that pays off once several agents share one server definition.
  2. The catalog's price is the catalog's limits. Zero code, zero install, zero keys for the ref route (DuckDuckGo over brave/tavily/exa precisely because no API key) — but the snapshot owns the exact image and the tool schemas (a newer release can change both), and key-required entries need secrets this phase deliberately left out of scope.
  3. MCP calls are not on the clearly-safe list. restricted refuses them by default — correct refuse-by-default behavior, and the refusal text is identical for a catalog tool and your own container; balanced with no human present surfaces The user rejected the tool call. So the unattended MCP template is a deliberate --safety autonomous one-shot.
  4. Build first, then the model-free check. docker build first; debug toolsets must list 11 tools with + echo (or + search) among them — it starts the toolsets and catches the missing image that the run itself shrugs off (exit 0, ⚠️, EOF handshake).
  5. The transcript is still the only judge. Restricted refusals, missing images and failed tool calls all exit 0; the response → transcript lines are the truth and the model's story is not — small models can believe they called a tool the system rejected.
