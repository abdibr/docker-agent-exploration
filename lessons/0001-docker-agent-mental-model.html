01The mental model, in three sentences

Read these carefully — everything else in this lesson hangs off them.

1. Docker Agent is Docker's open-source AI agent builder and runtime. You write a YAML file that names the models, the agents (role, instructions, tools), and how they connect — and the docker agent command turns that file into a running agent. It ships inside Docker Desktop 4.63+; on 4.49–4.62 the same tool was called cagent, which is why older tutorials use that name.

2. The config is the whole program. No wrapper scripts, no client code, no SDK — the YAML file alone runs the agent, as a live chat or as a one-shot printed run. This is the "no glue code" philosophy on display in ex01-first-agent/README.md.

3. Every connection type is one config edit away. External tools arrive through MCP (a ready-made catalog entry, or a server of your own in a container), extra teammate roles through sub_agents:, and the same config can be served to other programs through five different network doors. One file, seven flavors — exactly what the seven examples in this repo prove, in order.

Claim checks: the definition, rename history, and OCI sharing come from the official docs and the docker/docker-agent repo (whose README bills it as "AI Agent Builder and Runtime by Docker Engineering"). The "config is the whole program" phrasing and all run evidence come from ex01's README, recorded from verified runs on this machine.

🧩 Plain text you can version

Agents are YAML you can git-commit, diff, and review — like a Dockerfile, but for agents. One commit per example is how this whole repo was built.

🔌 Works with any provider

Named models: entries point at any provider. This repo pins the built-in ollama provider → local gemma4:latest on your own machine, and swapping to a cloud model is a one-line edit.

🤝 Connections built in

Built-in toolsets today (filesystem, shell, think); MCP for external tools; sub_agents for teammate roles; five serve doors for other programs.

02Anatomy of a real config — touch every part

This is ex01's actual agent.yaml — the smallest working Docker Agent in this repo. Five pieces of it are labeled on the right. For each label, click the matching line in the YAML.

# yaml-language-server: $schema=…/docker/docker-agent/main/agent-schema.json
models:
  gemma4_local:
    provider: ollama
    model: gemma4:latest
    description: Local gemma4 on the host Ollama daemon
agents:
  root:
    model: gemma4_local
    description: Ex01 first agent — smallest working Docker Agent
    instruction: |
      You are Ex01, the smallest working Docker Agent in the docker_agents repo.
      - For any question about a file, first read that file; quote exact values.
      - Before any multi-step task, write a short plan with the think tool.
    max_iterations: 20
    toolsets:
      - type: filesystem
        allow_list:
          - "."
      - type: shell
      - type: think

What each piece means (read after playing)
  • Named models entry — a friendly name (gemma4_local) wrapping provider + model string. Every agent references it by name, so changing the model is an edit in exactly one line — the repo's one-line local↔cloud swap (gemma4:latest → glm-5.3-flash:cloud).
  • The agent entry — root is the agent you actually talk to. Its description isn't just documentation: later examples show other programs reading it (in Ex05 it becomes the MCP tool's description; in Ex06 it appears on the A2A agent card).
  • The instruction — this is the prompt. The model sees it on every turn; the repo's rule ("first read the file, quote exact values") is what makes the verification answer come out the same way every time.
  • max_iterations: 20 — the turn budget, a runaway-loop fuse. Ex04 needs 12 for its lead, because delegation takes turns.
  • Toolsets — the abilities you list in the file. filesystem is sandboxed here with allow_list: ["."]: the agent can only touch its working directory. think gives the model a private scratchpad (gemma4 usually reasons in its own words, so it rarely calls it — not an error).

A real debugging moment from this config (recorded 2026-10-19)

On first verification, gemma4 called read_file with limit: 0 and got back invalid limit 0: limit must be >= 1 — then read the error, corrected itself, and retried. Lesson: small models trip on parameter corners, and clear tool errors are enough for them to fix themselves. That's also your first taste of the exit-code rule in the next section — the run still exited 0 either way.

03One config, many ways to run it

The config never changes shape — only the verb around it does. These are the run surfaces this repo actually used, all verified in docs/notes/run-modes.md.

VerbWhat happensWhere the repo leans on it

The verification template every example reuses (from ex01's README)

# Run headless; the answer itself is the assertion — exit 0 PLUS these two lines:
#   ollama gemma4:latest
#   filesystem shell think
docker agent run .\agent.yaml --exec 'Read agent.yaml in the current directory using your
filesystem tools. Then answer with exactly two lines. Line 1: the provider and the
model name you find under models. Line 2: the three toolset types listed for this agent.' --safety restricted
Why this task is clever: the answer lives entirely inside a file the agent must read, so one command is both the test and the runner — read-only, same result every time, no leftover files. The repo's rule: one command per example, judged only on what appears in the output (phase-notes.md §7).

🛡 --safety restricted

Fail-closed means: when in doubt, refuse. Built for runs with nobody watching. Obviously-safe calls (this read) auto-approve; everything else is silently denied — the denial only shows in the transcript, never as a prompt. The repo's default for verification.

⚡ --safety autonomous / --yolo

Auto-approve everything. Reserved for deliberate one-shot commands — the MCP examples (Ex02/Ex03) verify this way because restricted refuses MCP calls.

🎚 The full ladder

default | strict | balanced | restricted | autonomous (Ex07 exposes it as a switchable session mode). Serving surfaces default to restricted at startup.

🚨 The single most important operating lesson: exit 0 is not success

Refused tool calls, missing tool images, loops that repeat the same failed call — all still exit 0. In Ex01–Ex03 the refusal only appears as a transcript line like Tool 'write_file' is denied by the restricted safety mode…. Judge the transcript (or the protocol output), never the exit code. Every gotcha list in this repo repeats it: phase-notes §4.

04The map: seven examples, six ways to connect

Ex01 is the baseline (no special connections — just the agent itself). The other six examples test the ways to connect. Distilled from docs/notes/flavors.md, the repo's decision cheat-sheet. Memorize these four one-liners — they're the whole map:

🔧 MCP

Wires tools into an agent — or exposes the agent out as one tool.

🌐 A2A

Delegates work between agents over a network — they find each other and trade tasks with task state.

🧩 sub_agents

Multi-role work inside one config — delegation with zero extra networking setup.

📝 ACP

The editor-facing seat — the human's tool is the peer.

The decision flow — six questions, in this order (flavors.md's rule order)
  1. Can you split by role? Delegate tasks and roles inside one config → native sub_agents (Ex04). A lead plus specialists is simpler than any networked option — try it first.
  2. Who owns the work? If the agent needs tools from MCP, next question: does a catalog entry (Ex02) already cover it? If yes, stop — strongest isolation, zero code. If not…
  3. …build a custom MCP server (Ex03) when you need exact, testable tools you wrote yourself. This is the "custom" slot when no catalog entry covers the capability.
  4. Is the other side an MCP client? Your agent's skills should appear as tools in Claude Code etc. → serve mcp (Ex05).
  5. Do separate agent programs need to find each other and hand over whole tasks? → serve a2a (Ex06).
  6. Is the other side the human's editor? The editor starts your agent and drives it in-session → serve acp (Ex07).

⚠ Cross-flavor caution #1

MCP tool references work only on the top-level agent — sub-agents in one config cannot carry them (flavors.md rule §4), and Ex02's catalog ref: sits only under agents:.root. Delegation is Ex04's sub_agents; MCP stays on the main agent.

⚠ Cross-flavor caution #2

MCP vs A2A. MCP handles quick, back-and-forth tool calls; A2A hands over whole tasks that run on their own time, with discovery. Don't add A2A to fix an MCP problem.

⚠ Cross-flavor caution #3

Serving beyond your machine is network exposure — Ex05's HTTP mode listens on all network interfaces (0.0.0.0) by default. Local use on your own machine is fine, as we tested it; lock down access before sharing with other computers.

Ground truth: every claim here traces to repo docs — flavors.md (table, isolation stories, cross-flavor rules), example READMEs for what was verified — plus the public Agent Catalog and MCP Gateway pages for Ex02/Ex03. The two documented, never probed surfaces are excluded from every decision rule.

05The five things to carry forward

  1. Config is the whole program. A YAML file alone runs the agent — as a chat, as a one-shot run, or served. Anything the agent does should be expressible in the YAML file.
  2. Five keys are the vocabulary. models: entries (named, swappable), agents: with instruction/description, max_iterations as the fuse, toolsets: as capabilities, allow_list as the sandbox.
  3. Run modes are just different commands. Chat window for demos, --exec for recorded test runs, --dry-run to check the config for free. Pick by what evidence you need.
  4. The exit code can lie; the transcript tells the truth. Refused calls, broken toolsets, stuck loops — all can still exit 0. Read the transcript, then judge.
  5. The map: try sub_agents first; among the networked options, try catalog MCP first. Custom MCP when you need exact behavior; serve mcp/a2a/acp when the other side picks the protocol. Catalog tools beat custom servers when one exists — strongest isolation for free.
